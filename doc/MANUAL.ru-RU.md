<a id="what"></a>
## 1. Что такое модули

localSIEM состоит из **ядра** и **модулей**. Ядро хранит события, выполняет по ним поиск, применяет правила, группирует оповещения, отправляет их в SOC и следит за собственным состоянием. Каждый модуль добавляет одну службу сервера: он находит её журналы, читает их, превращает их в события, решает, что уже отражено, приносит собственные правила и проверяет требования этой службы.

Модули этого проекта устанавливаются в `/opt/localsiem/modules/<name>/`. Сейчас их два: **apache2** («Apache + ModSecurity», разделы 4–10) и **privesc** («Повышение привилегий», разделы 11–16). У localSIEM нет собственных модулей: страница «Модули» показывает только модули, установленные из этого репозитория.

<a id="installation"></a>
## 2. Установка и обновление модулей

Сначала должен быть установлен localSIEM; его установщик устанавливает только ядро и никогда не устанавливает модули. Модули этого проекта устанавливаются **только из веб-интерфейса localSIEM**: у этого проекта нет собственного установщика. Веб-интерфейс скачивает их из репозитория `https://github.com/PYMEHackers/localSIEM-modules` (ветка `main`). Модулям нужен localSIEM 2.2.0 или новее.

**Установка.** Войдя как администратор, откройте Модули › **Устанавливаемые** (раздел 3), нажмите **Проверить репозиторий**, посмотрите **Требования** (что нужно модулю на сервере и команды, которые это устанавливают; их нужно выполнить до установки модуля), а затем нажмите **Установить** у модуля. После этого localSIEM:

1. скачивает репозиторий и безопасно распаковывает его (ничего за пределами его папки, ограничения размера);
2. копирует папку модуля (`mod-<name>/` в репозитории) в `/opt/localsiem/modules/<name>/` без `tests/` (и без кэшей Python); модуль, установленный повторно, получает обратно свои прежние настройки;
3. перезапускает сборщик, который загружает модуль в течение нескольких секунд;
4. убирает модуль из списка и открывает диалоговое окно «<модуль> установлен» с командой, которую нужно выполнить от имени root на сервере (`manage.py setup-modules`), и кнопкой **Копировать**: команда даёт пользователю `localsiem` право чтения папок, перечисленных в `read_paths` его `module.json` (`/var/log/apache2` для модуля apache2, `/var/log/audit` для модуля privesc), в том числе файлов следующих ротаций, и перезапускает localSIEM. Этого права чтения модулю достаточно: у модулей нет параметров настройки, и они никогда не меняют сервер (разделы 8 и 11). Пока команда не выполнена, модуль может показывать «Ошибка»: его журналы ещё нельзя прочитать. Диалоговое окно закрывается кнопкой «Закрыть» или «Показать установленные модули», которая открывает вкладку «Установленные».

**Обновление.** Когда открывается Модули › **Установленные**, веб-интерфейс проверяет репозиторий, и модуль, для которого там есть более новая версия, показывает уведомление с кнопкой **Обновить** (раздел 3). После вашего подтверждения localSIEM скачивает новую версию и ставит её на место установленной (шаги 1–3), сохраняет её настройки и оставляет модуль включённым или выключенным, как он был. Команда для root показывается снова, только если новая версия читает другие журналы (`read_paths`); иначе ничего выполнять не нужно. Обновление localSIEM сохраняет установленные модули и их право чтения.

**Переустановка.** Веб-интерфейс не переустанавливает модуль и не устанавливает его более старую версию: чтобы переустановить модуль, нажмите **Удалить** (раздел 3) и снова установите его на вкладке **Устанавливаемые**; его настройки сохраняются.

**Установка модуля никогда не устанавливает отслеживаемое им ПО.** Модуль apache2 не устанавливает ни Apache, ни ModSecurity, а модуль privesc не устанавливает ни auditd, ни демон syslog, ни snoopy. Если при первой установке на сервере нет того, что нужно модулю (Apache и ModSecurity для apache2; для privesc — источника, который может читать `localsiem`, раздел 14), модуль устанавливается **выключенным**: диалоговое окно вместо команды перечисляет, чего не хватает, и модуль нельзя включить, пока **Перенастроить** не обнаружит недостающее (раздел 4). Обновление оставляет модуль включённым или выключенным, как он был.

<a id="modules-page"></a>
## 3. Страница «Модули»

Администраторы открывают **Администрирование › Модули**, где есть два раздела, каждый по своему адресу: **Установленные** (`/admin/dashboard/modules/installed/`), который открывается по умолчанию (`/admin/dashboard/modules/` ведёт туда), и **Устанавливаемые** (`/admin/dashboard/modules/installable/`). Аналитики видят **Модули** в своей панели (`/user/dashboard/modules/`): только список установленных модулей, только для чтения, без разделов.

**Установленные** показывает по одной строке на каждый установленный модуль во всю ширину: его название, его id, его версию, метку состояния, его краткое описание и под ним — причины этого состояния. Список обновляется сам каждые 10 секунд. Если ни один модуль не установлен, показывается «Установите модули на вкладке Устанавливаемые.» (аналитикам: «Модули не установлены. Их устанавливает администратор в разделе Модули › Устанавливаемые.»).

| Состояние | Значение |
|---|---|
| **Включён и работает** | Включён, загружен сборщиком и читает свои источники. Предупреждения диагностики показываются как примечания, но не меняют состояние. |
| **Включён, есть предупреждения** | Включён, но не найдено журналов для чтения, какой-то источник ещё не существует или модуль был установлен после запуска сборщика (перезапустите службу `localsiem`). |
| **Ошибка** | Модуль не загружается (ошибка показывается), его диагностика сообщает об ошибке или источник нельзя прочитать (права пользователя `localsiem`). |
| **Выключен** | Выключен или установлен без своих требований (для apache2: нет Apache или ModSecurity; для privesc: `localsiem` не может читать ни журнал auditd, ни syslog), как указано в его причине. |
| **Применение изменения…** | Только что включён или выключен: сборщик применяет изменение. |
| **Неизвестно** | Сборщик (служба `localsiem`) не запущен, поэтому ничего не читается. |

Когда модуль не выключен, строка также показывает: **Читаемые источники** (читаемые / найденные), **Строки (1 ч)**, **Последние данные**, **События (24 ч)**, **Заблокировано (24 ч)** и счётчики **Диагностики** («OK: n · предупреждений: n · ошибок: n»).

Администраторы также получают в каждой строке:

- **Переключатель** каждого модуля. Выключение модуля требует подтверждения: localSIEM перестаёт читать его журналы и отправлять его оповещения, пока модуль не будет снова включён; уже сохранённое остаётся. Включение сразу начинает чтение. Пока какое-либо требование модуля не выполнено, переключатель заблокирован («Выключен: не выполнены требования»): **Перенастроить** (раздел 4) разблокирует его, как только обнаружит недостающее.
- **Настроить**, кнопка, которая открывает страницу модуля, `/admin/dashboard/modules/installed/<name>/` (раздел 4); старый адрес `/admin/dashboard/modules/<name>/` ведёт туда же.
- **Удалить**, в том числе у модуля, который не загружается (и на странице модуля). После вашего подтверждения localSIEM удаляет `/opt/localsiem/modules/<name>/` и перезапускает сборщик без него: тот перестаёт читать его журналы и отправлять его оповещения. Уже сохранённые события по-прежнему доступны для поиска, а его настройки остаются на случай повторной установки. Право чтения его журналов, которое root дал `localsiem`, не отзывается.
- **Обновить**, когда в репозитории есть более новая версия модуля. Каждый раз, когда открывается вкладка «Установленные», веб-интерфейс проверяет репозиторий («Проверка новых версий в репозитории…»; браузер повторно использует ответ в течение 10 минут), и строка, для модуля которой есть более новая версия, показывает «В репозитории есть версия X (установлена Y).» с кнопкой **Обновить**. После вашего подтверждения localSIEM устанавливает новую версию (раздел 2), сохраняет её настройки, оставляет модуль включённым или выключенным, как он был, и перезапускает сборщик; диалоговое окно показывает команду для root, только если новая версия читает другие журналы. Если новой версии нужен более новый localSIEM, уведомление говорит «В репозитории есть версия X, но ей нужен localSIEM Z или новее: обновите localSIEM, чтобы установить её.» и не содержит кнопки.

**Устанавливаемые** (только для администраторов) содержит карточку «Устанавливаемые модули». **Проверить репозиторий** скачивает репозиторий и показывает модули, которые ещё не установлены на этом сервере, каждый с названием, id, версией и кратким описанием и с кнопкой или примечанием:

| Кнопка или примечание | Значение |
|---|---|
| **Требования** | Показывает, что нужно модулю на сервере, и команды, которые это устанавливают, от имени root и через sudo (см. ниже) |
| **Установить** | Устанавливает модуль (раздел 2) |
| «Нужен localSIEM X или новее» | Его нельзя установить: сначала обновите localSIEM |
| «Модуль в репозитории некорректен» | Его нельзя установить |

Уже установленные модули здесь никогда не появляются: они обновляются на вкладке «Установленные». Если установлены все модули репозитория, карточка сообщает «Все модули репозитория уже установлены.». После установки диалоговое окно «<модуль> установлен» показывает команду, которую нужно выполнить от имени root, чтобы `localsiem` мог читать журналы модуля (раздел 2), с кнопкой **Копировать**; пока она не выполнена, модуль может показывать «Ошибка»: его журналы ещё нельзя прочитать. Если на сервере нет того, что нужно модулю, диалоговое окно вместо этого перечисляет, чего не хватает, с подсказкой открыть модуль на вкладке «Установленные» (**Настроить**) и нажать **Перенастроить**, когда недостающее появится.

**Требования** открывает «<модуль>: требования»: что нужно модулю на сервере и команды, которые это устанавливают в системе этого сервера («Этот сервер: …»), объявленные модулем (`install_requirements` его `module.json`), дважды, каждый раз с кнопкой **Копировать**: **От имени root** и **Через sudo** (те же команды с `sudo` впереди). Выполните их на сервере до установки модуля: установка модуля никогда не устанавливает это ПО, и localSIEM никогда не выполняет эти команды. Для модуля apache2 в Debian: `apt-get -y update`, `apt-get -y install apache2 libapache2-mod-security2 modsecurity-crs`, `a2enmod security2 unique_id`, `cp --update=none /etc/modsecurity/modsecurity.conf-recommended /etc/modsecurity/modsecurity.conf` (она только создаёт конфигурацию ModSecurity, DetectionOnly, если её нет) и `systemctl restart apache2`; в Alpine — только Apache (`apk add apache2`, затем `rc-update` и `rc-service`, чтобы запустить его), потому что в Alpine нет пакета ModSecurity 2: пока ModSecurity не собран из исходного кода и не загружен, модуль остаётся выключенным. Для модуля privesc: `apt-get -y install auditd rsyslog` в Debian и `apk add audit` с запуском auditd при загрузке в Alpine; достаточно любого одного читаемого источника, а в контейнере auditd работать не может.

<a id="apache-page"></a>
## 4. Страница модуля Apache

`/admin/dashboard/modules/installed/apache2/` (только для администраторов; старый адрес `/admin/dashboard/modules/apache2/` ведёт туда же) состоит из пяти частей:

1. **Заголовок**: название, id, версия, путь установки (`/opt/localsiem/modules/apache2`), переключатель, состояние с его причинами и показатели из раздела 3. **Назад к установленным модулям** возвращает на вкладку «Установленные»; **Повторить обнаружение и диагностику** сразу заново читает конфигурацию Apache и обновляет диагностику; **Перенастроить** снова ищет Apache и ModSecurity (см. ниже); **Удалить** удаляет модуль (раздел 3) и возвращает на вкладку «Установленные».
2. **Настройки**: форма из раздела 5. **Сохранить настройки** проверяет каждое значение и, если какое-то неверно, сообщает, какое именно («Недопустимое значение: …»).
3. **Источники**: каждый читаемый журнал, с колонками **Тип** (`access`, `error`, `audit`), **Путь**, **Vhost**, **Строки (1 ч)**, **Не разобрано (1 ч)**, **Последние данные** (например, `2026/10/29@13:59:59.723`) и **Состояние** (ошибка, если его нельзя прочитать, предупреждение, если он ещё не существует). Ниже — найденные, но не читаемые журналы с причиной: «журнал через канал (piped log), не поддерживается», «охвачен директивой GlobalLog, которая пишет все vhost» или «в его формате нет данных: каждая строка — один и тот же текст (псевдоним LogFormat, который не определён)».
4. **Диагностика**: проверки из раздела 7 со временем их выполнения. Каждое невыполненное требование (ModSecurity, CRS, `SecRuleEngine`, `mod_unique_id`, право чтения у `localsiem`) сопровождается фрагментом конфигурации или командой, которая его устраняет, и кнопкой **Копировать**. Проверки, касающиеся журналов, только описывают их и то, что localSIEM может из них прочитать, без исправления: журналы клиента никогда не изменяются (раздел 8).
5. **Правила**: правила из раздела 9, каждое с колонками **Вкл.**, **Правило** (название, id и категория), **Критичность**, **Порог** и **Окно (с)**, и кнопка **Сохранить правила**.

**Требования и Перенастроить.** Пока нет Apache или ModSecurity, модуль выключен, а заголовок перечисляет, чего не хватает, с командой, которая это устанавливает. **Перенастроить** (в том числе когда модуль выключен) снова ищет их с сохранёнными настройками; если Apache находится в нестандартном месте, сначала задайте **Файл конфигурации Apache** (раздел 5). Когда найдено и то и другое, кнопка разблокирует переключатель —включать модуль или нет, решаете вы— и показывает команду, которую нужно выполнить от имени root, чтобы `localsiem` мог читать журналы Apache, созданные после установки модуля. Включённый модуль, который лишился Apache или ModSecurity, остаётся включённым: об этом сообщают диагностика и предупреждения о состоянии (раздел 10).

**Каждое изменение применяется сразу, без перезапуска чего-либо**: веб-интерфейс сохраняет его и сообщает сборщику, который перезагружает свои настройки, заново обнаруживает источники и запускает диагностику. Если сборщик не отвечает, веб-интерфейс сообщает об этом, и изменение применяется при запуске сборщика.

<a id="settings"></a>
## 5. Настройки модуля Apache

| Настройка | По умолчанию | Что она делает |
|---|---|---|
| **Только источники ниже** | выкл. | Не обнаруживать журналы по конфигурации Apache: читать только источники, добавленные вручную. |
| **Источники, добавленные вручную** | нет | Журналы, которые читаются помимо обнаруженных (или вместо них, если включён параметр выше). До 50. |
| **Файл конфигурации Apache** | пусто | Пусто: определяется автоматически (`/etc/apache2/apache2.conf` в Debian, `/etc/apache2/httpd.conf` в Alpine; `/etc/httpd/conf/httpd.conf` тоже распознаётся). Абсолютный путь означает, что вместо этого используется указанный файл, если он существует. |
| **Интервал обнаружения (секунды)** | 3600 | Как часто конфигурация Apache перечитывается, чтобы найти новые vhost и журналы (от 60 до 86400). |
| **Порог блокировки ModSecurity** | 0 | 0: берётся из конфигурации CRS (`tx.inbound_anomaly_score_threshold` в `crs-setup.conf`), а если его там нет — 5. Используется, чтобы отличать срабатывание выше порога блокировки от срабатывания ниже него, когда сообщения ModSecurity сами не указывают порог (от 0 до 1000). |
| **Дни обучения для новых PHP-файлов** | 3 | В первые дни после первого запуска модуля ранее не встречавшийся PHP-файл не считается новым для правила `apache-webshell` (от 0 до 365). Файл, созданный или изменённый в его DocumentRoot за последние сутки, всегда считается новым. |

У каждого **источника, добавленного вручную**, есть такие поля (* обязательное):

| Поле | Назначение |
|---|---|
| **Тип** * | `access.log`, `error.log` или `Журнал аудита ModSecurity` |
| **Путь** * | Абсолютный путь к файлу |
| **Vhost** | Vhost строк, для журналов, в строках которых он не указан |
| **LogFormat** | Для журналов доступа: псевдоним (`localsiem_combined`, `combined`, `vhost_combined`, `common`, `combinedio` или определённый в конфигурации Apache) или сам формат. Пусто: пробуются обычные форматы. |
| **Тип журнала аудита** | `Последовательный (один файл)` или `Параллельный (по файлу на каждый запрос)` |
| **Папка хранения аудита** | Для параллельного типа: папка из `SecAuditLogStorageDir` |

Файл читается только один раз, даже если он одновременно обнаружен и добавлен вручную. Источник, который появляется во время работы localSIEM, читается с начала, если его размер 5 МБ или меньше, а иначе — с конца.

Две настройки раздела **Администрирование › Настройки** localSIEM также влияют на этот модуль: **Окно корреляции** (5 секунд: сколько ожидаются три записи запроса) и **Критичность ниже порога блокировки** (`low`). Запрос, отмеченный ModSecurity, также ждёт свою запись аудита, которую ModSecurity пишет по завершении запроса, до 2 минут: так медленный запрос не разбивается на два события.

<a id="soc"></a>
## 6. Что модуль Apache отправляет в SOC

Для каждого запроса модуль объединяет строку журнала доступа, строки журнала ошибок и запись аудита с одним и тем же `UNIQUE_ID`. В журналах доступа, которые Apache пишет по умолчанию (`combined`, `vhost_combined`, `common`), нет `UNIQUE_ID`: тогда каждая строка журнала доступа объединяется с записью аудита и строками журнала ошибок своего запроса по IP клиента, методу, URI, коду ответа и времени (±2 секунды), даже когда один и тот же запрос повторяется в ту же секунду, и событие помечается как «слабая корреляция». Vhost берётся из `%v` или, если в формате его нет, из заголовка Host и порта записи аудита, выбранных так же, как их выбирает Apache; время берёт микросекунды из записи аудита. Затем модуль решает, было ли с запросом уже что-то сделано («принятое действие»), читая сначала журнал аудита (`Action: Intercepted (phase N)`), а затем error.log (`Access denied with code NNN (phase N)`). Ответ 403 без следов ModSecurity не считается блокировкой: он помечается как сомнительный.

| Ситуация | Уходит в SOC? |
|---|---|
| Заблокирован ModSecurity в фазах 1-2 (приложение его так и не получило) | **Нет.** Остаётся в localSIEM, доступен для поиска (`action:blocked`) и учитывается в контексте следующего оповещения по этому IP. |
| Заблокирован в фазах 3-4 (приложение его уже выполнило) | Да |
| Срабатывания правил при движке в режиме `DetectionOnly` | Да |
| Срабатывания правил ниже порога блокировки | Да |
| Сигналы правил из раздела 9 | Да |

Критичность оповещений, вызванных срабатываниями ModSecurity (файл `severity.yaml` модуля):

| Ситуация | Критичность |
|---|---|
| Незаблокированные срабатывания, ответ 3xx, 4xx или 5xx | средняя |
| Незаблокированные срабатывания, ответ 2xx | высокая |
| Заблокирован в фазах 3-4 | высокая |
| Признаки успеха: сработало правило для исходящего трафика (950-955) и ничего не было заблокировано, или за запросом последовала ошибка базы данных | критическая |
| Ниже порога блокировки (часто ложное срабатывание на само приложение) | низкая (критичность ниже порога из Администрирование › Настройки) |

У каждого оповещения есть постоянное название (например, «Apache/ModSecurity: SQL injection not blocked (CRS 942)»), описание, которое заканчивается запросом для вставки в поиск localSIEM (например, `ip:203.0.113.7 category:sqli`), и подробности: vhost, IP клиента, метод, URI (замаскированный), ответ, user agent и данные ModSecurity (движок, действие, фаза, оценка аномальности, порог, правила и совпавшие данные). При отправке оповещение также несёт контекст IP: запросы и заблокированные запросы за последний час, правила, которые его заблокировали, и время, когда он был замечен впервые.

Пароли, cookie, заголовки `Authorization` и токены маскируются до того, как что-либо сохраняется, в том числе внутри тел запросов, а тела запросов никогда не передаются в SOC. Тело ответа (часть E) и полный текст выполненных правил (часть K) журнала аудита никогда не сохраняются.

<a id="doctor"></a>
## 7. Требования к Apache и ModSecurity: диагностика

Диагностика модуля apache2 читает конфигурацию Apache (не изменяя её) и проверяет каждое требование. Она запускается при старте сборщика, после каждого изменения настроек, при каждом обнаружении, по кнопке **Повторить обнаружение и диагностику** и командой `manage.py doctor` (раздел 17), только пока модуль включён: пока он выключен из-за отсутствия Apache или ModSecurity, страница модуля вместо этого показывает эти требования (раздел 4). Статусы: OK, предупреждение (работает с ограничениями), ошибка (нужно исправить) и информация (важна только в некоторых ситуациях).

| Проверка | В порядке, когда | Если нет |
|---|---|---|
| Конфигурация Apache | `apache2.conf` или `httpd.conf` (или заданный файл) найден и прочитан | Ошибка: добавьте источники вручную (раздел 5). Части, которые нельзя прочитать, перечисляются как предупреждения. |
| ModSecurity | `mod_security2` (ModSecurity 2) загружен | Ошибка. Debian: `apt-get install libapache2-mod-security2 modsecurity-crs && a2enmod security2`. В Alpine пакета нет: соберите mod_security2 2.9 из исходного кода. ModSecurity 3 (libmodsecurity) не поддерживается. |
| OWASP CRS | Файлы CRS подключены (диагностика показывает, сколько их, и порог аномальности) | Ошибка: `apt-get install modsecurity-crs` или подключите `crs-setup.conf` и `rules/*.conf` после ModSecurity |
| SecRuleEngine | `On` (запросы выше порога блокируются в фазе 2 и остаются в localSIEM) или `DetectionOnly` (ничего не блокируется: каждое срабатывание уходит в SOC) | Ошибка, если `Off`; предупреждение, если `Off` везде, кроме некоторых vhost, если директивы нет (тогда ModSecurity по умолчанию использует `Off`) или если некоторые vhost задают `Off` |
| mod_unique_id | Загружен: ModSecurity работает, и три источника запроса объединяются по `UNIQUE_ID` | Ошибка, если ModSecurity загружен: без него ModSecurity 2 ничего не проверяет (Alpine его не загружает); иначе предупреждение (слабая корреляция). Debian: `a2enmod unique_id`; Alpine: `LoadModule unique_id_module modules/mod_unique_id.so` |
| Формат журнала доступа | В журналах доступа есть IP клиента, время, строка запроса и код ответа, как в форматах, которые Apache пишет по умолчанию (OK, «Access logs in the format Apache writes»): каждая строка объединяется с записями ModSecurity своего запроса по IP клиента, методу, URI, коду ответа и времени. Если в формате есть миллисекунды, vhost и `UNIQUE_ID` (например, `localsiem_combined` на серверах, которые его уже пишут), они объединяются по `UNIQUE_ID` (OK, «Access log with milliseconds, vhost, duration and UNIQUE_ID») | Информация, без исправления, если в журнале доступа нет чего-то из этих четырёх: localSIEM читает его как есть, но не может объединить его строки с записями ModSecurity (эти запросы видны в журнале аудита); информация, если не читается ни один журнал доступа (запросы видны в журнале ошибок и в журнале аудита). Формат журналов принадлежит клиенту (раздел 8) |
| mod_remoteip | Загружен с `RemoteIPHeader` | Информация, без исправления: если сайт находится за прокси или балансировщиком нагрузки, в журналах будет IP прокси, как и в оповещениях и в правилах по IP |
| Журнал аудита | `SecAuditEngine RelevantOnly` (или `On`) с `SecAuditLog` | Предупреждение, если он выключен: localSIEM принимает решения только по error.log, а в карточке запроса нет заголовков и списка правил. Когда он включён, его примечания только описывают его: параллельный тип (по файлу на каждую транзакцию; ModSecurity обычно создаёт их с правами 600, и localSIEM читает их, если `localsiem` может), собственный формат (читается как есть), записывается часть E (она никогда не уходит в SOC), нет части H (принятое действие нельзя прочитать из журнала аудита; единственное примечание, из-за которого проверка становится предупреждением). Исправления нет: журнал аудита настраивает клиент (раздел 8) |
| Маскирование в источнике | Есть действие `sanitise` | Информация, без исправления («The audit log on disk is not masked»): файл, который пишет ModSecurity, может содержать пароли и cookie; localSIEM маскирует их перед сохранением, и они никогда не уходят в SOC |
| Права доступа | `localsiem` может читать каждый источник | Ошибка. Debian: `usermod -aG adm localsiem`; Alpine: показанные команды `setfacl`. Источник, который ещё не существует, — это только информация. |
| Журналы через канал | — | Предупреждение: `\|/usr/bin/rotatelogs ...` и syslog прочитать нельзя; пишите журнал также в файл или добавьте источник вручную |
| Журнал доступа без данных | — | Предупреждение: `CustomLog` использует формат, который не определяет ни один `LogFormat` (или `LogFormat` без единой директивы `%`), поэтому Apache пишет один и тот же текст в каждой строке, без IP клиента, времени и запроса. localSIEM не читает этот журнал и видит запросы его vhost в его журнале ошибок и в журнале аудита ModSecurity. Формат журналов сервера никогда не меняется. |
| Движок в режиме Off | — | Ошибка: записи аудита сообщают, что движок выключен |
| Версия ModSecurity | — | Информация: версия, прочитанная из журнала аудита |

Когда в конфигурации есть `GlobalLog`, формат которого содержит `%v` (он пишет все vhost), остальные журналы доступа не читаются: они бы только повторяли его строки. Диагностика никогда не предлагает менять формат журналов или настройки журнала аудита (раздел 8).

<a id="client-logs"></a>
## 8. Журналы клиента никогда не изменяются

Модуль apache2 только **читает** журналы Apache и ModSecurity: он никогда не пишет в них, не ротирует, не усекает, не перемещает и не удаляет их и никогда не меняет ни их формат, ни конфигурацию Apache или ModSecurity, которая их пишет. Если сервер пишет журналы в собственном формате (например, собственный `LogFormat` или IP клиента, который даёт `mod_remoteip`), модуль подстраивается под него: он читает каждый журнал доступа в том формате, который использует его `CustomLog`. Диагностика (раздел 7) только описывает журналы и то, что localSIEM может или не может из них прочитать, не предлагая их менять; исправление она даёт только для того, что не является журналом: ModSecurity, CRS, `SecRuleEngine`, `mod_unique_id` и права чтения пользователя `localsiem`. Единственное, что для этого модуля делается от имени root, — это право чтения (`manage.py setup-modules`, раздел 2).

В версиях модуля 1.2.0 и более ранних был параметр настройки `--configure-apache`, удалённый в версии 1.3.0. На серверах, где он был применён, остаётся записанный им файл `/etc/apache2/conf-available/localsiem.conf` (Debian) или `/etc/apache2/conf.d/localsiem.conf` (Alpine) с форматом `localsiem_combined` и его `GlobalLog` (`localsiem_access.log`), настройками журнала аудита и `SecAction`, который маскирует чувствительные значения. Пока этот файл на месте, модуль читает эти журналы, как любые другие. Чтобы отменить это, удалите этот файл (Debian: `a2disconf localsiem`) и перезагрузите Apache. В Alpine этот файл также загружал `mod_unique_id` и `mod_logio`: перед его удалением загрузите `mod_unique_id` в другом месте конфигурации Apache, потому что без него ModSecurity 2 ничего не проверяет (раздел 7). Установщик localSIEM удаляет этот файл при `--uninstall` или `--reinstall` (в Alpine сначала загрузите `mod_unique_id` в другом месте) и оставляет журналы (`localsiem_access.log`, `modsec_audit.log`) там, где они есть.

<a id="rules"></a>
## 9. Правила модуля Apache

Правила применяются к каждому событию. Сигнал правила всегда уходит в SOC. На странице модуля каждое правило можно выключить, а также изменить его критичность, порог (от 1 до 100000) и окно (от 1 до 86400 секунд); порог и окно применяются только к пороговым правилам и правилам последовательности. Его события можно найти с помощью `rule:localsiem:<id>`.

| Правило | Тип | Критичность | Когда | Порог / окно |
|---|---|---|---|---|
| `apache-bruteforce` «перебор паролей на странице входа» | пороговое | средняя | Незаблокированные запросы POST с одного IP к странице входа одного vhost (`/wp-login.php`, `/xmlrpc.php`, `/administrator/index.php`, `/user/login`, `/login`, `/admin/login`, `/login.php`, `/admin.php`, `/signin`, `/auth/login`, `/phpmyadmin/index.php`) | 20 за 300 с |
| `apache-login-after-bruteforce` «успешный вход после перебора паролей» | последовательность | высокая | Не менее 10 неудачных входов (POST с ответом 200, 401 или 403) на странице входа, затем вход с ответом 302 или 303 (WordPress отвечает 200 на неудачный вход и 302 на удачный) | 10, в пределах 1800 с |
| `apache-enumeration` «перечисление (всплеск ответов 404)» | пороговое | средняя | Незаблокированные ответы 404 одному IP от одного vhost | 30 за 60 с |
| `apache-sensitive-file` «отдан чувствительный файл» | совпадение | высокая | Ответ 2xx на файл, который не должен быть публичным: `.env`, `.git/`, `.svn/`, `.hg/`, `.htaccess`, `.htpasswd`, дампы и резервные копии (`.sql`, `.sql.gz`, `.bak`, `.old`, `.orig`, `.swp`, `.save`, `.backup`, `.dump`, имена, оканчивающиеся на `~`), `phpinfo`, `info.php`, `server-status`, `server-info`, копии `wp-config.php` и `config.php`/`config.inc`, `.DS_Store`, закрытые ключи SSH, `composer.json`/`composer.lock`, `.aws/`, `backup.zip`/`.tar`/`.tar.gz`/`.tgz`/`.rar` | — |
| `apache-webshell` «возможный веб-шелл (POST к новому PHP-файлу)» | совпадение | критическая | POST с ответом 2xx к PHP-файлу, созданному или изменённому в его DocumentRoot за последние сутки или впервые замеченному за последний час (после дней обучения) | — |
| `apache-db-error-after-attack` «ошибка базы данных после подозрительного запроса» | последовательность | критическая | Запрос, на котором сработали правила CRS, и с того же IP — ошибка базы данных (SQL или PDO) в error.log | 1, в пределах 30 с |

<a id="health"></a>
## 10. Предупреждения о состоянии модуля Apache

Помимо предупреждений о состоянии самого localSIEM, модуль не реже чем раз в 5 минут проверяет и отправляет в SOC:

| Предупреждение | Критичность | Что делать |
|---|---|---|
| ModSecurity больше не загружен | высокая | Он был загружен, а теперь нет: запросы не проверяются. Если никто не сделал этого намеренно, возможно, кто-то выключил защиту. |
| Движок ModSecurity переведён в Off | высокая | `SecRuleEngine` изменён на `Off`, или журнал аудита сообщает, что движок выключен. Проверьте конфигурацию Apache и её недавние изменения. |
| Нет реального IP клиента (mod_remoteip) | средняя | За последний час не менее 90 % из не менее чем 100 запросов пришли с одного частного или локального адреса: вероятно, сайт находится за прокси, и Apache записывает IP прокси, поэтому правила по IP для этих запросов не работают. Отправляется не чаще раза в сутки. |

То, о чём уже было сообщено, запоминается между перезапусками, поэтому обновление не отправляет это повторно. Благодаря этим предупреждениям включённый модуль никогда не выключается сам, когда исчезает Apache или ModSecurity.

<a id="privesc"></a>
## 11. Модуль повышения привилегий

Модуль **privesc** («Повышение привилегий») отслеживает, что люди и службы запускают на сервере, и сообщает о шагах повышения привилегий до root: разведке, поиске setuid-программ, инструментах перечисления вроде linpeas, известных эксплойтах, обратных оболочках (reverse shell), получении root без sudo или su, оставленных бэкдорах и попытках ослепить мониторинг. Он также проверяет поверхность атаки сервера: setuid-программы, capabilities и чувствительные файлы, доступные другим для записи (раздел 16).

Он читает только то, что уже есть на сервере: он никогда ничего не устанавливает, никогда не загружает правила аудита и никогда не меняет конфигурацию auditd, snoopy или оболочек. Он читает до двух источников:

| Источник | Что он видит | Где работает |
|---|---|---|
| **auditd** (`/var/log/audit/audit.log`) | sudo, su, pkexec и входы по SSH (PAM), а также всё, что записывают правила аудита сервера (см. ниже) | Физические серверы и виртуальные машины, пока работает auditd. **Не внутри контейнера** (LXC, podman, systemd-nspawn, Docker): аудит ядра не разделён по пространствам имён, поэтому auditd работает только на хосте. |
| **syslog** (`/var/log/auth.log`, `/var/log/secure` или `/var/log/messages`) | sudo, su, pkexec, doas, входы по SSH и, если установлен **snoopy**, каждая запущенная программа | Везде, включая контейнеры. Читается, когда auditd не запущен, его журнал нельзя прочитать или установлен snoopy (настройка **Читать syslog**). Нужен демон syslog, который пишет в файл: сам по себе журнал systemd не читается. |

Что показывает auditd, зависит от правил аудита, которые загружает сервер и которые определяет его администратор; модуль использует их как есть, какими бы ни были их ключи, и классифицирует каждую запись по её типу, системному вызову и файлам:

| Модуль видит | Когда правила аудита сервера записывают |
|---|---|
| Каждую запущенную программу (в том числе из скриптов, веб-шеллов и эксплойтов), setuid-программы, унаследованный от них root, полученные capabilities | `execve` |
| Изменения учётных записей, sudoers, PAM, preload, SSH, cron, служб и `/etc/audit` | Наблюдения (`-w ... -p wa`) за этими файлами или системные вызовы, которые их меняют |
| Установку битов setuid или setgid | `chmod`, `fchmod`, `fchmodat` |
| Загрузку или выгрузку модулей ядра | `init_module`, `finit_module`, `delete_module` |
| Процессы, к которым подключились через ptrace | `ptrace` |
| Отказы человеку в доступе к файлам | `open`, `openat`, `execve`..., которые завершаются ошибкой `EACCES` или `EPERM` |
| Удаление правил аудита, выключение аудита, остановку auditd, аварийное завершение программ | Всегда (о них сообщают ядро и auditd) |

На физическом сервере или виртуальной машине auditd — это источник, которого пользователь не может избежать; диагностика сообщает, что правила аудита сервера записали на данный момент (раздел 14). В контейнере snoopy — единственный способ видеть каждую запущенную программу.

Встроенные команды оболочки (`pwd`, `cd`, `unset HISTFILE`, `history -c`) никогда не запускают программу, поэтому их не видит ни один источник, кроме случаев, когда они находятся внутри командной строки вроде `bash -c '...'`. Один `whoami` никогда не становится оповещением: модуль считает **различные** команды разведки каждого сеанса в пределах окна, и оповещением становится только их всплеск (раздел 13).

Что содержит каждое событие модуля и как по нему искать:

| Колонка | Содержит | Пример поиска |
|---|---|---|
| `vhost` | Человека: пользователя, под которым выполнен вход (он остаётся тем же при sudo и su) | `module:privesc vhost:alice` |
| `method` | Тип события: `exec` (запущенная программа, auditd или snoopy), `sudo`, `su`, `pkexec`, `doas`, `login`, `pam`, `file` (изменён чувствительный файл), `chmod` (бит setuid), `kmod`, `ptrace`, `denied` (отказ в доступе к файлу), `audit_config`, `auditd`, `crash`, `syscall` (другой системный вызов, записанный правилами аудита сервера) | `module:privesc method:sudo` |
| `uri` | Командная строка (пароли замаскированы) | `module:privesc uri:*linpeas*` |
| `path` | Запущенная программа или изменённый файл | `module:privesc path:/tmp/*` |
| `ip` | SSH-адрес сеанса, если он известен | `module:privesc ip:203.0.113.7` |
| `score` | Различные команды разведки сеанса в окне | `module:privesc score:>=8` |
| `action` | `blocked`, когда сама система это остановила: программа, которую не удалось запустить, отказ sudo или su, отказ в доступе к файлу | `module:privesc action:blocked` |
| `source` | `audit` или `syslog` | `module:privesc source:syslog` |

Правила о попытках (повторные неудачи sudo, много отказов в доступе к файлам) всё равно учитывают заблокированные события; остальные смотрят только на то, что действительно было выполнено.

Страница модуля, `/admin/dashboard/modules/installed/privesc/`, состоит из тех же частей, что и страница модуля Apache (раздел 4): заголовок (с кнопками **Повторить обнаружение и диагностику**, **Перенастроить** и **Удалить**), настройки (раздел 12), источники (`audit`, `syslog`; а также не читаемые, с причиной), диагностика (раздел 14) и правила (раздел 13).

При отправке оповещение также несёт контекст сеанса: было ли замечено его начало, прошёл ли он через sudo или su, его SSH-адрес и его **последние 20 команд**, чтобы аналитик видел, что привело к оповещению, без поиска.

Одну и ту же команду может увидеть более одного источника (auditd и snoopy): оповещения группируются по модулю, пользователю, IP, категории и критичности, поэтому всё равно получается одно оповещение. Пароли в командных строках (`mysql -p...`, `sshpass -p`, `curl -u user:pass`, `PASSWORD=...`, URL с паролем) маскируются до того, как что-либо сохраняется, в том числе в шестнадцатеричном виде в записях аудита.

<a id="privesc-doctor"></a>
## 14. Требования модуля повышения привилегий: диагностика

**Требования.** Модулю нужен один источник, который может читать пользователь `localsiem` (файл существует, и `localsiem` может его открыть): журнал **auditd** (auditd работает, вне контейнера) или файл **syslog** с sudo, su, pkexec и doas (`/var/log/auth.log`, `/var/log/secure` или `/var/log/messages` либо настройка **Файл syslog**, если только **Читать syslog** не имеет значения Никогда), куда **snoopy**, если он установлен, также записывает каждую запущенную программу. Достаточно любого из них. Когда источник существует, но `localsiem` не может его прочитать, требование сообщает об этом и приводит команду, которая даёт право чтения (для журнала аудита — команду со страницы «Модули», `manage.py setup-modules`; для syslog — `setfacl -m g:localsiem:r <file>`). Если нет ни одного, оно сообщает, что установить: auditd (Debian: `apt-get install auditd`; Alpine: `apk add audit && rc-update add auditd && rc-service auditd start`), демон syslog (Debian: `apt-get install rsyslog`; Alpine: `apk add rsyslog && rc-update add rsyslog && rc-service rsyslog start`) или snoopy. До этого модуль остаётся выключенным; **Перенастроить** выполняет проверку снова. Сам модуль ничего не устанавливает. При первой установке журналы обычно принадлежат root: выполните команду, которую показывает веб-интерфейс, затем нажмите **Перенастроить**.

Диагностика работает так же, как у Apache (раздел 7). Она только описывает, что модуль видит с тем, что есть на сервере, и чего он видеть не может; её исправления — это только пакеты для установки и право чтения для `localsiem`. Она никогда не предлагает менять правила аудита, `auditd.conf` (кроме `log_group`, см. ниже), `snoopy.ini`, оболочки или любую другую конфигурацию:

| Проверка | В порядке, когда | Если нет |
|---|---|---|
| auditd | auditd работает | Предупреждение, если он не установлен (Debian: `apt-get install auditd`; Alpine: `apk add audit && rc-update add auditd && rc-service auditd start`); предупреждение без исправления, если он установлен, но остановлен (запускать ли его, решает администратор). Информация внутри контейнера: там auditd работать не может. |
| Журнал аудита | `localsiem` может его читать | Ошибка с командой со страницы «Модули»; предупреждение, если auditd работает, а его журнал находится не там, где модуль его ищет (настройка **Журнал аудита**) |
| Группа журнала аудита | Журнал аудита не принадлежит группе `root` | Предупреждение, если принадлежит (`log_group = root` в `auditd.conf`): каждый журнал, который auditd создаёт при ротации, получает права 600, доступен для чтения только root, и localSIEM перестаёт его читать. Исправление — строка `log_group = adm` для `/etc/audit/auditd.conf` (затем перезапустите auditd): новые журналы создаются с правами 640. |
| Записи правил аудита | Прочитаны запуски программ (`EXECVE`) | Предупреждение, если auditd пишет, но ни одна из его записей не является запуском программы: правила аудита сервера не записывают `execve`, поэтому команды скриптов, веб-шеллов и эксплойтов через auditd не видны. Информация о том, что ещё правила записали на данный момент (изменения чувствительных файлов, биты setuid, модули ядра, ptrace, отказы в доступе к файлам), и о том, чего пока не было |
| syslog | Файл syslog читается | Ошибка, если его нельзя прочитать (`setfacl -m g:localsiem:r <file>`); предупреждение, если нет ни пригодного журнала аудита, ни файла syslog (Debian: `apt-get install rsyslog`; Alpine: `apk add rsyslog && rc-update add rsyslog && rc-service rsyslog start`) |
| snoopy | Установлен, и его строки читаются | Предупреждение без auditd: команды скриптов и веб-шеллов не видны (Debian: `apt-get install snoopy`; в Alpine пакета нет: его собирают из исходного кода). Предупреждение, если он установлен, но syslog не читается. Информация, если в его строках нет эффективного uid (`message_format` в `snoopy.ini`): root, унаследованный от setuid-программы, через snoopy не виден |
| Что видит модуль | — | Информация: auditd (и что записывают его правила), snoopy (каждая запущенная программа) или, как предупреждение, только sudo, su, pkexec и doas (syslog без snoopy: большинство правил не могут сработать); ошибка, если он ничего не может прочитать. Также напоминает, что встроенные команды оболочки никогда не видны |
| Файлы версии 1.0.0 | — | Информация без исправления, если найдены файлы, которые оставил `--configure-privesc` (раздел 15) |
| Setuid-программы и capabilities | — | Информация: последнее сканирование (раздел 16). Предупреждение без исправления с setuid-программами, которые дают оболочку root (GTFOBins), и с программами, capabilities которых на практике равнозначны root |
| Чувствительные файлы | Ни один не доступен для записи никому, кроме root | Ошибка без исправления для каждого из них (`/etc/passwd`, `sudoers`, cron, `/etc/profile.d`, папки `PATH` пользователя root, `docker.sock`...) |
| Привилегированные группы | — | Предупреждение без исправления с участниками `docker`, `lxd`, `incus-admin`, `disk` и `libvirt`: на практике они являются root |

<a id="privesc-legacy"></a>
## 15. Серверы, обновлённые с версии 1.0.0 модуля повышения привилегий

В версии 1.0.0 модуля были параметр настройки `--configure-privesc` и хук bash; версия 1.1.0 удалила и то и другое, потому что модуль никогда ничего не устанавливает и не меняет за пределами `/opt/localsiem`. На серверах, где он был применён, остаётся то, что он записал, и localSIEM это не использует и не удаляет:

- `/etc/audit/rules.d/90-localsiem-privesc.rules`: его правила аудита (ключи `lsiem_*`). Пока они загружены, модуль читает их записи так же, как записи любого другого правила сервера.
- `/etc/localsiem-privesc/` (хук), `/etc/profile.d/localsiem-privesc.sh` и строка, следующая за «localSIEM privesc: command hook» в `/etc/bash.bashrc` (Debian) или `/etc/bash/bashrc` (Alpine): пока они на месте, каждый интерактивный bash продолжает записывать свои команды в `/var/log/localsiem-privesc/`, которые никто не читает.
- `/var/log/localsiem-privesc/`: файлы команд каждого пользователя.
- `log_group = adm` в `/etc/audit/auditd.conf`, `/root/.ssh` (создана пустой) и `message_format` в `/etc/snoopy.ini`: их можно оставить (`log_group = adm` сохраняет ротированные журналы аудита доступными для чтения, раздел 14, а модуль читает этот формат snoopy так же, как и его форматы по умолчанию).

Диагностика перечисляет те из них, которые может увидеть (проверка «Files of version 1.0.0 of the module»). Чтобы удалить их, от имени root: удалите файл правил и снова загрузите правила (`augenrules --load`); удалите `/etc/profile.d/localsiem-privesc.sh`, `/etc/localsiem-privesc/` и строку в bashrc; и удалите `/var/log/localsiem-privesc/`, если не хотите сохранять содержащиеся там команды.

<a id="privesc-health"></a>
## 16. Поверхность атаки и предупреждения о состоянии модуля повышения привилегий

Помимо своих правил модуль проверяет сам сервер и отправляет в SOC:

| Предупреждение | Критичность | Когда |
|---|---|---|
| Новая программа setuid или setgid | высокая | Сканирование находит программу setuid или setgid, которой не было при предыдущем сканировании (первое сканирование служит только эталоном). Злоумышленник, получивший root, часто оставляет после себя setuid-оболочку; добавить такую программу может и обновление пакета. |
| Новая setuid-программа в папке, доступной для записи | критическая | То же самое в `/tmp`, `/var/tmp`, `/dev/shm`, `/home`, `/srv` или `/var/www` |
| Новая setuid-программа из GTFOBins | критическая | То же самое для программы, которая с битом setuid даёт оболочку root (`bash`, `find`, `python`, `vim`, `less`, `cp`...) |
| Новые capabilities | высокая | Программа получила capabilities, которые на практике равнозначны root (`cap_setuid`, `cap_dac_override`, `cap_sys_admin`...) |
| Чувствительный файл доступен для записи не только root | критическая | Проверяется каждый час: `/etc/passwd`, `/etc/shadow` (также доступный для чтения всем), `sudoers`, cron, `/etc/profile.d`, PAM, службы, `ld.so.preload`, папки `PATH` пользователя root, `docker.sock`... Сообщается один раз для каждого файла и проблемы. |
| auditd остановлен (состояние localSIEM) | высокая | auditd работал, а теперь нет (вне контейнеров) |

Сканирование выполняется в фоне, не чаще чем раз в **Часы между сканированиями setuid-программ** (первое — через пять минут после запуска сборщика), по **Сканируемым папкам**, от имени пользователя `localsiem` (то, что он не может прочитать, пропускается), и останавливается после 3 миллионов файлов или 15 минут. Его результат с найденными GTFOBins и capabilities показывается в диагностике. Критичность этих предупреждений задана в `severity.yaml` модуля. То, о чём уже было сообщено, запоминается между перезапусками.

## 17. Командная строка

От имени root, `/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py <command>`:

| Команда | Назначение |
|---|---|
| `modules` | Установленные модули: id, версия, включён, выключен или не загружен, и папка, с невыполненными требованиями, если они есть; а также модули, которые не удалось загрузить, с ошибкой |
| `doctor` | Для каждого включённого модуля: каждая проверка (`✓`, `!`, `✗`, `·`) с фрагментом, который её исправляет, и найденные источники; для модуля, выключенного из-за невыполненного требования, — его требования. `--json` выдаёт то же самое в виде JSON. |
| `read-paths` | Папки, которые читают модули и к которым localSIEM даёт право чтения от имени root |
| `setup-modules [--no-restart]` | От имени root: команда, которую показывает веб-интерфейс; право чтения папок модулей (`read_paths`) и перезапуск localSIEM (`--no-restart`: без него). У модулей нет параметров настройки |

Запустите диагностику от имени пользователя `localsiem`, чтобы увидеть его реальные права:

```bash
runuser -u localsiem -- /opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py doctor   # Debian
su -s /bin/sh localsiem -c "/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py doctor"   # Alpine
```
